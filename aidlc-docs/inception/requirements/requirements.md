# Requirements — 바이낸스/업비트 거래소별 추천 5개씩 포함

## Intent Analysis Summary
- **User Request**: "Using AI-DLC 추천 리스트를 바이낸스, 업비트 기준 각각 5개씩 포함될 수 있도록 추가해주고, 바이낸스 거래량 최상위 20개로 추천 5개 찾아줘."
- **Request Type**: Enhancement / New Feature — Unit 1(data-pipeline), Unit 2(analytics-backtest), Unit 3(api-service) 모두에 걸침
- **Scope Estimate**: Multiple Components
- **Complexity Estimate**: Complex — 신규 후보 소스 추가, 신규 데이터 수집 경로, 추천 결합 로직 변경, DB 스키마 변경
- **Depth Applied**: Standard

## Code Investigation Findings
- 현재 추천 후보는 **업비트 KRW 마켓 거래대금 상위 20개**(`MarketSelector`, BTC/ETH 제외)에서만 산출된다. 바이낸스는 오직 BTC/ETH 4시간봉을 "시장 레짐(regime) 필터" 참고용으로만 사용하고, 바이낸스 자체 코인은 추천 후보가 된 적이 없다.
- 바이낸스에서는 4시간봉만 수집한다(BTC/ETH regime 용). 1시간봉 골든크로스 시그널 계산에 필요한 바이낸스 1시간봉은 전혀 수집되지 않는다.
- `src/data_store.py`는 이미 `Source = Literal["upbit", "binance"]`로 소스별 캔들 테이블이 분리되어 있어, 바이낸스 코인에 대해서도 기존 `compute_ichimoku`/`golden_cross_event`/`compute_signal_stats` 로직을 그대로 재사용할 수 있다(신규 알고리즘 불필요).
- `recommendations` 테이블/`Recommendation`/`RecommendationRecord`에는 거래소 구분 컬럼이 없다 — 마켓 심볼 형식이 달라(`KRW-XXX` vs `XXXUSDT`) 문자열 충돌은 없지만, API/알림에서 거래소를 명시적으로 표시하려면 신규 컬럼이 필요하다.

| 2 | 거래소별 신호 통과 코인이 5개 미만일 때 처리 | 있는 만큼만 포함 — 기존 기대수익률 4% 임계값(BR7)을 유지, 미달 시 강제로 채우지 않음 (0~5개 가변) |

## Functional Requirements
- FR-B1: 바이낸스에서도 업비트와 동일한 방식으로 "거래대금 상위 20개 후보"를 산출한다 — 대상은 USDT 마켓, BTC/ETH(레짐 참고용) 제외, 스테이블코인 페어 및 레버리지 토큰 페어 제외(Q1).
- FR-B2: 바이낸스 후보 코인에 대해 1시간봉/4시간봉을 업비트 후보와 동일한 방식(부트스트랩/증분)으로 수집·저장한다.
- FR-B3: 바이낸스 후보 코인에 대해 기존과 동일한 시그널(골든크로스 + 4시간봉 구름대 추세 + 레짐 필터 + 기대수익률 4% 임계값)로 추천 여부를 판정한다 — 판정 로직 자체는 거래소와 무관하게 재사용(신규 알고리즘 없음).
- FR-B4: 최종 추천 리스트는 업비트 상위 5개(기대수익률 내림차순) + 바이낸스 상위 5개(기대수익률 내림차순)로 구성한다. 각 거래소에서 임계값을 통과한 코인이 5개 미만이면 있는 만큼만 포함한다(Q2) — 총 0~10개.
- FR-B5: 각 추천 항목에 거래소 구분(`source`: "upbit" | "binance")을 추가해 저장·조회·알림 모두에 노출한다.
- FR-B6: `GET /recommendations`, `POST /run` 응답 및 텔레그램/디스코드 알림 메시지에 거래소 구분을 표시한다.
- FR-B7 (명시적 비범위): 시그널 계산 알고리즘(golden cross, ichimoku, 기대수익률 계산) 자체는 변경하지 않는다 — 기존 로직을 소스만 다르게 하여 재사용.

## Non-Functional Requirements
- NFR-B1 (Consistency): 바이낸스 후보 선정/캔들 수집은 기존 업비트 파이프라인과 동일한 장애 격리 원칙(RESILIENCY-10, 개별 마켓 실패가 다른 마켓에 영향 없음)을 따른다.
- NFR-B2 (Schema Evolution): 이미 배포된 DB(`recommendations` 테이블에 기존 데이터 존재)에도 안전한 마이그레이션(컬럼 추가, 기존 행은 `source='upbit'`로 채움)을 사용한다 — 과거 데이터는 전부 업비트 추천이었으므로 이 기본값이 사실과 일치한다.
- NFR-B3 (Rate/Load): 바이낸스 후보 20개 추가로 인한 API 호출 증가가 기존 재시도/백오프/타임아웃 정책(이미 구현됨) 안에서 처리되어야 한다 — 새 정책 불필요.

# 추가 요청 (2026-08-10): 추천 발생 빈도 개선

## Intent Analysis Summary
- **User Request**: "지금 이더랑 비트가 상승채널에 온게 아닌가. 계속 추천 코인이 없네"
- **Request Type**: Defect-suspicion → 조사 결과 **버그 아님**, 튜닝 요청으로 전환
- **Depth Applied**: Minimal (진단 중심) + 실측 기반 의사결정

## 진단 결과 (실측)
사용자 지적대로 **BTC/ETH 레짐 게이트는 정상 통과 중**이었습니다 (BTC 65,049 / ETH 1,919, 둘 다 구름 위 + 양운, 최근 5회 실행 모두 `regime_bullish=1`). 서비스도 정상 가동 중이었고(도커 컨테이너 healthy, 스케줄러 매시 실행, 현재 후보 40개 모두 12분 이내 신선한 데이터), 데이터 수집 문제도 아니었습니다.

진짜 병목은 **BR4의 "정확히 최신 봉에서 골든크로스"** 조건이었습니다. 현재 신선한 후보 40개 중 최신 봉 교차 발생 코인이 0개였고, 30일 시뮬레이션 결과 이 조건으로는 **평균 103시간(약 4일)에 1회**만 추천이 발생했습니다.

## Clarifying Answers (AskUserQuestion)
| # | Question | Answer |
|---|---|---|
| 1 | 어느 쪽을 완화할지 (1차) | "기대수익률 임계값 낮춤" — 이후 실측으로 **기각됨** (아래) |
| 2 | 실측 데이터 확인 후 최종 결정 | **골든크로스 3봉 확대, 임계값 4% 유지** |

1차 답변(임계값 인하)은 실측 근거를 제시해 재확인했습니다: 임계값을 0%까지 없애도 빈도 천장이 28시간 간격에 불과한 반면 적중률은 81%→40%로 반토막 났고, 3봉 기준에서 4%→3%는 아무 변화도 없었습니다. 즉 임계값은 유효한 레버가 아니었습니다.

## Functional Requirements
- FR-F1: 골든크로스 판정을 "정확히 해당 봉"에서 "해당 봉 포함 최근 `GOLDEN_CROSS_LOOKBACK_BARS`(=3)봉 이내 발생"으로 완화한다 (Unit 2 BR4).
- FR-F2: 백테스트 표본 수집도 동일한 진입 기준을 사용해, `expected_return`이 실제 추천이 제안하는 진입 시점의 기대값과 일치하도록 유지한다 (Unit 2 BR8).
- FR-F3: 기대수익률 임계값 4%는 **변경하지 않는다** (실측상 무의미하거나 품질만 저하).
- FR-F4 (명시적 비범위): 적중 판정 기준의 4%(`hit_count`, `target_reached`)는 서비스 목표이자 성과 지표 정의이므로 그대로 유지한다 — 추천 필터의 4%와 혼동하지 않는다.

## Out of Scope
- 적중률 기반 필터(평균 수익률 대신 "과거 4% 도달률 N% 이상")로의 전환 — 옵션으로 제시했으나 미채택.
- 바이낸스 실주문/인증 연동 (여전히 공개 API만 사용).

# 추가 요청 (2026-08-10): 추천 신뢰도 향상

## Intent Analysis Summary
- **User Request**: "신뢰도는 높아져야해. 표본이 많아져서 발생한 케이스야?? 4%랑 3%랑 표본 차이가 심해??"
- **Request Type**: 질문 2건 + 품질 개선 요구 → 조사 결과 **버그 2건 발견**
- **Depth Applied**: Standard (실측 기반)

## 질문에 대한 실측 답변
**Q1. "표본이 많아져서 발생한 케이스인가?"** → 그렇습니다. 3봉 완화로 표본이 78 → 238개(3.1배)가 됐지만 **실제 교차는 78 → 83건(+6%)** 에 불과했습니다. 코인별 중복배수가 거의 정확히 3.0배로, 늘어난 표본은 대부분 같은 교차의 복사본이었습니다.

**Q2. "4%와 3%의 표본 차이가 심한가?"** → 표본 차이가 아니라 **분포 공백**입니다. 기대수익률 순서가 `17.01% → 13.95% → 5.16% → 4.69%` 다음 곧바로 `2.77% → 2.45%`로 떨어져, **3~4% 구간에 코인이 0개**입니다. 그래서 임계값을 3%로 낮춰도 아무 변화가 없었습니다.

## 조사 중 발견한 결함 2건
- **결함 1 (추정량 편향)**: 중복 표본이 `expected_return` 값 자체를 왜곡. 교차마다 확인 봉 수(1~3개)가 달라 가중치가 불균등하게 붙음. `KRW-ONDO`가 -0.88% → +2.32%로 부호 반전.
- **결함 2 (이력 수집 누락)**: 바이낸스 이력이 설정(180일)의 1/4.5인 41일만 수집됨. `binance_client.py`의 `min(limit, _MAX_LIMIT)`이 Binance의 요청당 1,000개 상한에서 조용히 잘리고 페이지네이션이 없었음. 업비트는 184일 정상 수집되어 거래소 간 표본 규모가 어긋나 있었음.

## Clarifying Answers (AskUserQuestion)
| # | Question | Answer |
|---|---|---|
| 1 | 적용 범위 | **버그 2건 수정 + 최소 교차 3회** |
| 2 | 바이낸스 이력 길이 | **업비트와 동일하게 180일** (거래소 간 통계 비교 가능성 확보) |

## Functional Requirements
- FR-R1: 바이낸스 캔들 수집에 페이지네이션을 적용하고, 이미 저장된 마켓도 설정된 lookback까지 소급 백필한다 (Unit 1 BR10). 판단 기준은 "마지막 캔들"이 아니라 **"최초 캔들"** — 증분 경로는 앞으로만 진행하므로 과거를 채울 수 없다.
- FR-R2: 백테스트 표본을 **교차 1건당 1개**로 중복 제거해 추정량 편향을 제거한다 (Unit 2 BR8).
- FR-R3: 과거 교차가 `MIN_SIGNAL_SAMPLES`(=3)회 미만인 코인은 기대수익률이 임계값을 넘어도 추천하지 않는다 (Unit 2 BR15).
- FR-R4 (명시적 비범위): 기대수익률 임계값 4%와 골든크로스 3봉 창은 변경하지 않는다.

## 달성 결과 (실측)
- 바이낸스 이력 1,007봉(41일) → **4,320봉(180일)**, BTC/ETH 4시간봉도 1,080봉(180일)로 확장
- 바이낸스 코인 평균 교차수 3.5회 → **7.5회**
- 자격 코인 4개 → 2개(EPICUSDT, BANKUSDT). 탈락한 `ZECUSDT`(+5.16% → **-0.67%**)와 `KRW-WLD`(교차 1회)는 **짧은 이력·중복 표본이 만들어낸 거짓 양성**이었음

# 추가 요청 (2026-08-10): 진입 가이드 및 24시간 유효기간

## Intent Analysis Summary
- **User Request**: "하루에 4%, 3% 수익볼 코인 추천하는거라서, 하루 이상을 넘기면 안되 추천대상이. 진입 시점도 가이드에 포함해줘."
- **Request Type**: Enhancement (유효기간 + 진입 가이드) → 조사 중 **버그 1건 추가 발견**
- **Depth Applied**: Standard

## 조사에서 확인한 것
- **유효기간 없음**: `GET /recommendations`가 `get_latest_run()`을 나이 제한 없이 반환. 스케줄러가 멈추면 며칠 전 추천이 현재 추천처럼 나감.
- **진입 정보 전무**: 응답·알림 어디에도 진입 시각/가격/목표가/청산 기한이 없음.
- **버그 — 미완성 봉 사용**: 두 거래소 모두 응답 마지막에 진행 중인 봉을 주는데 그걸 최신 봉으로 사용 중이었음(실측 07:01:50에 2분치 07:00 봉 반환). BR7의 "가장 최근 **마감된** 1h 봉" 및 `scheduler.py`의 ":05에 실행해 봉 마감을 기다린다"는 의도와 모두 모순. 진입가를 확정값으로 제시할 수 없게 만드는 전제 결함이라 함께 수정.

## Clarifying Answers (AskUserQuestion)
| # | Question | Answer |
|---|---|---|
| 1 | 24시간 지난 추천 처리 | **목록을 비우고 `expired` 사유 표시** |
| 2 | 가이드 포함 항목 | 진입 시각+기준가, 목표가(+4%), 청산 기한(+24h), 손절가 |
| 3 | 손절가 (실측 후 재확인) | **낙폭 통계로 대체** — 데이터가 특정 손절 수준을 지지하지 않음 |

손절가는 표본 184건으로 검증 후 재질문했습니다: 4% 도달 표본의 중앙값 낙폭(-1.89%)과 미도달 표본(-2.74%)이 거의 겹쳐 구분력이 없고, 어떤 손절 수준도 평균 수익률을 유의하게 개선하지 못했으며(0.24~0.46%, 노이즈 범위), -2% 손절은 결국 목표에 도달했을 사례의 47%를 잘라냈습니다. 근거 없는 숫자 대신 관측된 사실만 제공하기로 했습니다.

## Functional Requirements
- FR-G1: 모든 지표·시그널 판정은 구간이 끝난 봉만 사용한다 — 진행 중인 봉은 저장 단계에서 제외 (Unit 2 BR6-0).
- FR-G2: 추천마다 진입 시각·진입 기준가·목표가(+4%)·청산 기한(+24h)·과거 최대 낙폭을 API와 알림에 제공한다 (Unit 2 BR16, Unit 3 BR12). 목표가와 청산 기한은 파생 계산하고 저장하지 않는다.
- FR-G3: 최신 회차가 24시간을 넘기면 `recommendations`를 비우고 `expired: true`로 반환한다. `history`와 `POST /run`은 영향받지 않는다 (Unit 3 BR13).
- FR-G4: 최대 낙폭은 **참고 정보**로만 제공하고 손절 지시로 표기하지 않는다. `expected_return`이 손절 없이 24시간 보유한 값임을 문서에 명시한다.

## Out of Scope
- 고정 손절가 — 데이터가 지지하지 않아 미채택 (위 근거 참조).
- 손절을 반영한 `expected_return` 재계산 — 손절 자체를 채택하지 않았으므로 불필요.

# Requirements — 백테스트 이력 1년(365일) 확대 (2026-08-11)

## Intent Analysis Summary
- **User Request**: "Using AI-DLC 180일 데이터 보다 더 많이 1년치 데이터 기준으로 처리될 수 있도록 변경해줘. 그리고 1년치 데이터는 저장하는거지?? 그래야 매번 호출 안하니까"
- **Request Type**: Enhancement — Unit 1(data-pipeline) 중심, Unit 2는 설정값 확대 효과만 받음
- **Scope Estimate**: Single Component (+ 설정)
- **Depth Applied**: Minimal — 요구가 명확하고 단일 설정값 + 그에 딸린 수집 경로 수정

## Code Investigation Findings
- **저장 여부(사용자 질문)에 대한 답: 저장한다.** 캔들은 `data/coin_recommender.db`(SQLite, 현재 33MB)에 `upbit_candles`/`binance_candles` 테이블로 영구 저장되고, 이력이 lookback 깊이에 도달한 마켓은 매 실행 **타임프레임당 1건**의 증분 요청만 보낸다. 매번 전체를 다시 받지 않는다.
- **다만 설정값만 365로 바꾸면 업비트에는 적용되지 않는다.** `_collect_and_store`는 부트스트랩 여부를 `get_last_candle_time is None`(DB가 비었는가)으로만 판정하므로, 이미 180일치가 있는 마켓은 증분 경로로만 들어가고 증분은 앞으로만 진행한다 → 과거는 영원히 채워지지 않는다. 바이낸스는 2026-08-10에 `get_first_candle_time` 기반 백필(BR10)이 이미 들어가 있어 자동 확대된다.
- 백테스트 표본은 BTC/ETH 4시간봉 레짐 통과가 조건이므로, 레짐 기준 종목 이력도 함께 365일이 되어야 새 이력이 실제 표본으로 이어진다. 두 종목 모두 동일한 `backtest_lookback_days`를 쓰므로 자동으로 충족된다.
- 성능 상한 확인: 백테스트 스캔의 `as_of` 선형 탐색은 골든크로스가 발생한 봉에서만 호출되어(전체의 약 2%) 봉 수에 사실상 선형. 이력 2배는 문제되지 않는다.

## Functional Requirements
- FR-Y1: `backtest_lookback_days`를 180 → **365**로 변경한다 (`config/settings.yaml` 및 `src/config.py` 기본값 동시 변경 — 둘이 어긋나면 컨테이너/로컬 동작이 갈린다).
- FR-Y2: 업비트 수집에 소급 백필 경로를 추가해, 이미 저장된 마켓도 설정된 lookback까지 과거를 채운다 (Unit 1 BR11). 판정 기준은 **최초 캔들**이며, 백필 요청 범위는 **비어 있는 과거 구간만**으로 제한한다.
- FR-Y3: 정상 상태(이력이 lookback에 도달)에서의 실행당 요청 수는 변경 전과 동일해야 한다 — 즉 저장된 데이터를 재사용하고 매 실행 전체 재수집을 하지 않는다 (사용자 요구 "매번 호출 안하니까").

## Out of Scope
- 상장이 1년 미만인 코인에 대해 "더 이상 과거가 없음"을 영구 기록하는 상태 테이블 — 백필 범위를 과거 구간으로 한정해 상시 비용이 타임프레임당 1건으로 줄었으므로, 별도 상태 저장 없이 단순하게 둔다.
- 바이낸스 백필의 요청 범위 축소 — 요청당 1,000봉이라 비용이 업비트의 1/5이고, 기존 동작(BR10)이 검증되어 있어 건드리지 않는다.
- 오래된 캔들 정리(retention) — DB는 약 66MB 예상으로 문제되지 않는다.
