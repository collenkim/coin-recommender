# Business Rules — Unit 3: api-service

## BR1. 파이프라인 오케스트레이션 순서 (services.md 재확인)

1. `MarketSelector.get_candidate_markets()`
2. 후보/BTC/ETH 캔들 수집 및 저장 (Unit 1)
3. `Scorer.generate_recommendations()` (Unit 2) — 내부에서 레짐 하드필터 적용
4. 결과를 `pipeline_runs` + `recommendations` 테이블에 저장
5. `Notifier.send_notification()` 호출 (best-effort, 실패해도 파이프라인은 성공으로 간주)

## BR2. 동시 실행 방지

프로세스 내 락(예: `threading.Lock`)으로 파이프라인 중복 실행을 막는다. 이미 실행 중일 때 `POST /run`이 호출되면 파이프라인을 새로 시작하지 않고 "이미 실행 중" 응답(409)을 반환한다. 스케줄러 잡도 동일 락을 공유한다.

## BR3. 결과 저장은 항상 발생, 알림은 best-effort

파이프라인이 레짐 하드필터로 추천 0개를 반환하더라도 `pipeline_runs`에 실행 기록은 남긴다 (regime_bullish=False로). `Notifier` 전송이 실패(네트워크 오류 등)해도 예외를 상위로 전파하지 않고 로그만 남기며, 이미 저장된 결과는 그대로 유지된다.

## BR4. 알림 채널

`.env`에 `TELEGRAM_WEBHOOK_URL`, `DISCORD_WEBHOOK_URL` 중 설정된 것마다 각각 발송. 하나만 설정되면 하나만, 둘 다 없으면 알림을 보내지 않고 로그만 남긴다 (에러 아님).

## BR5. 알림 메시지 형식

```
[coin-recommender] {run_time} 추천 결과

- {market}: 기대수익률 {expected_return:.1%} (과거 {n}회 중 {hit_count}회 적중)
- ...

(추천 없음이면: "이번 회차 추천 없음")
```

## BR6. GET /recommendations 응답

`pipeline_runs`에서 가장 최근 `run_time`을 조회 → 해당 `run_time`의 `recommendations` 행 전체 반환. 아직 한 번도 실행되지 않았으면 (`pipeline_runs`가 비어있으면) 빈 결과 + `run_time: null`을 반환 (에러 아님, 정상적인 초기 상태).

## BR7. GET /health

DB 연결을 확인하는 간단한 쿼리(`SELECT 1`)를 실행해 성공하면 `{"status": "ok", "db_connected": true}`, 실패하면 500과 함께 `{"status": "error", "db_connected": false}` 반환 (RESILIENCY-06).

## BR8. POST /run 동기/비동기

`POST /run`은 파이프라인 실행이 끝날 때까지 기다렸다가(동기) 결과를 반환한다 (스펙에 "수동 트리거"라고만 되어 있고 별도 비동기 요구가 없으므로 가장 단순한 방식 채택 — 매시 실행이 몇 분 내 끝나는 규모라 응답 지연이 크지 않음).

## BR9. 추천 결과 판별 배치 (신규 — Requirements Q3/Q4)

- `run_recommendation_pipeline()` 본연의 흐름(BR1) 끝에서, 판별 대상(Unit 2 BR12) 추천 건들을 모두 조회해 `Backtest.evaluate_outcome()`(Unit 2 BR11)을 호출하고 결과를 저장한다.
- 같은 락(BR2) 안에서 실행 — 스케줄러/`POST /run` 어느 쪽으로 트리거되든 동일하게 처리되고, 파이프라인과 동시 실행되지 않음.
- 개별 추천 건의 판별 실패(데이터 부족 등)는 로그만 남기고 나머지 건은 계속 처리한다 (BR7의 부분 실패 격리 패턴 재사용).
- 배포 이전 과거 추천 기록도 이 배치의 판별 대상에 자연히 포함된다 (Unit 2 BR12가 `evaluated_at IS NULL`인 모든 건을 대상으로 하므로 별도 백필 스크립트 불필요).

## BR10. GET /recommendations 확장 응답 (신규 — Requirements Q5, FR-L5)

- 쿼리 파라미터 `limit` (기본값 1).
- `limit=1`(기본, 파라미터 생략 포함)일 때: 응답의 최상위 구조(`run_time`, `regime_bullish`, `recommendations`)는 기존과 100% 동일하게 유지 (하위 호환) — 단, 각 `recommendations` 항목에 `target_reached`(bool | null)와 `realized_return`(float | null) 필드가 추가된다 (미판별이면 둘 다 null). 기존 클라이언트는 모르는 필드를 무시하므로 영향 없음.
- `limit>1`일 때: 위 최상위 필드는 그대로 최신 회차를 나타내고, 추가로 `history` 필드에 최근 `limit`개 회차(최신 포함, `run_time` 내림차순)를 같은 모양(`run_time`/`regime_bullish`/`recommendations`)의 리스트로 담아 반환한다. 저장된 회차가 `limit`보다 적으면 있는 만큼만 반환 (에러 아님).

## BR11. 거래소 구분 노출 (신규 — 거래소별 추천 5개씩 요청, Requirements FR-B5/FR-B6)

- `POST /run`, `GET /recommendations` 응답의 각 추천 항목에 `source`("upbit" | "binance") 필드를 추가한다.
- 알림 메시지(BR5)의 각 항목 앞에 거래소 구분을 표시한다: `- [{source}] {market}: 기대수익률 ...` (예: `- [upbit] KRW-XRP: ...`, `- [binance] SOLUSDT: ...`).
- `MarketSelector`/`Pipeline`이 이미 업비트 그룹 5개 + 바이낸스 그룹 5개 순서로 리스트를 구성해 넘기므로(Unit 2 BR14), API/알림은 받은 순서를 그대로 노출하기만 하면 된다 — 별도 재정렬/그룹핑 로직 불필요.

## BR12. 진입 가이드 노출 (신규 — 2026-08-10, Requirements FR-G2)

`GET /recommendations`와 `POST /run`의 각 추천 항목에 Unit 2 BR16의 진입 가이드를 포함한다:
`entry_time`, `entry_price`, `target_price`, `exit_deadline`, `max_drawdown`.

- `target_price`(진입가×1.04)와 `exit_deadline`(진입+24시간)은 **응답 시점에 파생 계산**하고 DB에 저장하지 않는다 — 저장하면 규칙 변경 시 값이 어긋난다.
- DB에는 `entry_time`, `entry_price`, `max_drawdown` 3개 컬럼만 추가한다(기존 ALTER TABLE 마이그레이션 방식 재사용, 기존 행은 NULL).
- 진입 정보가 없는 과거 행(이 기능 이전 데이터)은 해당 필드가 모두 `null`로 나가고, 알림에서는 가이드 줄 자체를 생략한다 — 없는 값을 만들어내지 않는다.
- 알림 메시지 형식:
```
- [binance] TUTUSDT: 기대수익률 0.4% (과거 21회 중 4회 적중)
    진입 0.2294 (08-10 04:00 UTC 종가 기준) → 목표 0.2386 (+4%)
    청산 기한 08-11 04:00 UTC (진입 +24시간)
    과거 동일 신호 최대 낙폭 -17.3% (손절 지시 아님, 참고용)
```

## BR13. 추천 유효기간 24시간 (신규 — 2026-08-10, Requirements FR-G3)

서비스가 예측하는 것은 **하루 안의 움직임**이므로, 추천은 진입 시점으로부터 24시간(백테스트 측정 구간과 동일)이 지나면 실행 대상이 아니다.

- `GET /recommendations`의 최신 회차가 `run_time + 24시간`을 넘겼으면 `recommendations`를 **빈 배열**로 반환하고 `expired: true`를 함께 준다. `run_time`은 그대로 유지해 "실행된 적 없음"(`run_time: null`)과 구분한다.
- 판정 기준으로 개별 `entry_time`이 아니라 회차의 `run_time`을 쓴다 — 한 회차의 모든 추천은 같은 시각대에 생성되므로 결과가 같고, 진입 정보가 없는 과거 행도 함께 처리된다.
- `history`(limit>1)는 만료와 무관하게 그대로 반환한다 — 실행 기록 조회 목적이지 실행 대상이 아니기 때문.
- `POST /run`은 방금 실행한 결과이므로 만료 판정을 적용하지 않는다.

**이 규칙이 실제로 필요한 이유**: 파이프라인은 매시 목록을 갱신하므로 정상 운영 중에는 만료가 발생하지 않는다. 그러나 스케줄러/컨테이너가 멈추면 `get_latest_run()`이 며칠 전 회차를 **현재 추천처럼** 반환하며, 하루 지난 진입가로 진입을 유도하게 된다. 만료 처리는 그 상황에 대한 안전장치다.

## BR22. 가격 도달 감시 스케줄러 (2026-08-11)

추천이 나온 뒤 24시간 동안 5분마다 진입가/매도가/손절가 도달을 확인하고, 도달 시 알림을 보냅니다.

**판정 기준**:
- **진입가 도달** = 추천 이후 저가가 진입가 이하로 내려온 시점. 추천 시점의 진입가는 그 순간의 종가라 이미 도달 상태이므로, "다시 진입가까지 내려와 지금 진입 가능해진 시점"으로 해석합니다.
- **매도가 도달** = 고가 >= 진입가 x 1.03
- **손절가 도달** = 저가 <= 진입가 x 0.98
- 한 봉에서 매도가와 손절가를 동시에 만족하면 `simulate_trade`(BR18)와 동일하게 **손절 우선**으로 봅니다.
- 매도가 또는 손절가에 닿으면 포지션이 끝난 것이므로 해당 종목 감시를 종료합니다.

**1분봉을 쓰는 이유**: 5분 간격의 시점 가격만 보면 그 사이에 스쳐간 도달을 놓칩니다. 백테스트가 고가/저가로 터치를 판정하므로 감시도 같은 기준이어야 합니다. `get_klines_since(symbol, "1m", entry_time)`으로 진입 이후 전체를 매번 다시 훑습니다 -- 별도의 "마지막 확인 시각" 상태를 두지 않아도 컨테이너 다운타임 중 발생한 도달을 놓치지 않습니다. 활성 추천 5건 기준 5분마다 최대 10요청(시간당 120요청)으로 Binance 레이트리밋 대비 여유가 큽니다.

**중복 방지**: `entry_touched_at` / `target_hit_at` / `stop_hit_at` 컬럼에 최초 도달 시각을 기록하고, `mark_price_event`는 NULL일 때만 UPDATE합니다. 기록 자체가 "이미 알렸다"는 표시이므로 별도 플래그가 없습니다. 이벤트가 없으면 알림을 보내지 않습니다 -- 5분마다 "변화 없음"을 보내면 하루 288통이 됩니다.

**스케줄**: `CronTrigger(minute="*/5")`, 파이프라인(매시 :05)과 별도 잡. 파이프라인 락을 공유하지 않습니다 -- 읽기 위주에 짧은 UPDATE만 하고, 시간당 1회 파이프라인이 도는 동안에도 감시는 계속되어야 합니다(SQLite WAL).

**발견한 결함 (같은 작업 중 수정)**: `TIMEFRAME_HOURS`에 `1m`이 없어 `drop_unclosed`가 KeyError를 냈고, 감시 루프의 예외 처리에 먹혀 **이벤트 0건으로 조용히 넘어갔습니다.** 목 클라이언트 단위 테스트로는 잡히지 않고 실제 거래소 호출에서만 드러난 종류입니다. 회귀 방지 테스트를 `test_data_store.py`에 추가했습니다.

## BR23. 시장 국면 문구 노출 (2026-08-18)

판정 규칙 자체는 Unit 2의 BR23을 따른다. 여기서는 **표시 방식**만 정한다.

### 알림 문구 (`notifier._format_message`)

헤드라인 한 줄 + 자산별 한 줄:

```
[coin-recommender] 추천 코인 0개
2026-08-18 09:20 KST

상승장 아님 — BTC·ETH가 함께 상승하고 있지는 않습니다
· BTCUSDT 비상승:  일 +2.6%  주 +0.9%  30일 -0.5%  월 -16.0%  년 -45.0%
· ETHUSDT 약상승:  일 +2.0%  주 +2.2%  30일 +2.7%  월 -9.4%  년 -57.2%

이번 회차 추천 없음
```

헤드라인 3종:
- 강상승장 — BTC·ETH 둘 다 상승 모멘텀이 강합니다
- 약상승장 — BTC·ETH 둘 다 상승 중이지만 강세까지는 아닙니다
- 상승장 아님 — BTC·ETH가 함께 상승하고 있지는 않습니다

문안에 "오른다"는 뜻이 읽히는 표현을 쓰지 않는다 — Unit 2 BR23대로 예측력을 주장할 근거가 없다.

### 추천 0건일 때도 넣는다

이 줄이 없으면 `"이번 회차 추천 없음"`이 **게이트가 닫혀서 0건인지, 열렸는데 통과한 코인이 없어서 0건인지** 구분되지 않는다 (2026-08-13 진단에서 기록된 문제). 그래서 추천 유무와 무관하게 항상 넣는다.

### 판정 불가 시 생략

이력이 모자라 판정할 수 없으면 **줄을 통째로 뺀다**. 모르는 것을 "상승장 아님"으로 적으면 데이터 결손이 시장 판단으로 둔갑한다. 한 자산만 판정 가능하면 그 자산만으로 판정한다(문구가 통째로 사라지는 것보다 낫다).

### API 노출 (`GET /recommendations`, `POST /run`)

최상위에 `market_phase`를 추가한다 (`phase`, `assets[].market/label/returns`).

- **저장하지 않고 조회 시점에 계산한다** — 국면은 회차의 속성이 아니라 현재 시장의 속성이다. DB 스키마는 건드리지 않는다.
- **`history`의 과거 회차에는 붙이지 않는다** — 붙이면 지난 회차가 그때의 국면이었던 것처럼 읽힌다.
- 기존 `regime_bullish`(진입 게이트)와는 **별개 기준이라 둘이 어긋날 수 있다.** 게이트는 BTC 30일 단독, 국면은 BTC/ETH 5구간이다.

## BR24. 2트랙 추천 노출 (2026-08-18)

판정 규칙은 Unit 2 BR24를 따른다. 여기서는 **저장·표시 방식**만 정한다.

### 트랙 구분 저장

`recommendations` 테이블에 `track` 컬럼 추가 (`'short'` | `'long'`, 기본값 `'short'`). 기존 행은 전부 단기 트랙이므로 기본값으로 그대로 유효하다 — **가산적 마이그레이션**이며 기존 조회는 영향받지 않는다(2026-08-07 outcome 컬럼 추가와 같은 방식).

### 알림 — 하나의 메시지, 트랙별 섹션

두 트랙을 **별도 발송하지 않는다**. 시간당 알림 수가 두 배가 되고, 한쪽만 0건일 때 "왜 안 왔는지"를 구분할 수 없다.

```
[coin-recommender] 추천 코인 3개
2026-08-18 09:00 KST

강상승장 — BTC·ETH 둘 다 상승 모멘텀이 강합니다
· BTCUSDT 강상승:  ...
· ETHUSDT 강상승:  ...

[단기] 24시간 내 +3% 목표 · 2개
(1) SOLUSDT ...
(2) XRPUSDT ...

[장기] 반감기 구간 · 90일 내 +20% 목표 · 1개
(1) DOGEUSDT
· 90일 내 +20% 도달 확률: 46%  (과거 74회 중 34회, 손절 -10% 적용 기준)
· 진입가 / 목표가 / 손절가 / 청산 기한
```

트랙별로 **0건이어도 섹션 제목은 남긴다** — 그래야 "게이트가 닫혀서 0건"임이 드러난다. 장기 트랙이 닫혀 있으면 사유를 한 줄로 적는다(예: `반감기 후 2.3년차 — 0~1년차 구간에서만 열림`).

### 유효기간 — 장기도 짧다

단기는 24시간(BR13). **장기는 4시간**(다음 4시간봉 마감까지)이다. 보유 기간이 90일이라고 진입 시점이 90일간 유효한 것이 아니다 — 측정된 진입은 "그 4시간봉 종가"이고, 며칠 뒤 다른 가격에 들어가면 측정된 매매가 아니다.

### 가격 도달 감시 (BR22)

장기 추천도 감시 대상에 포함하되 **트랙별 목표·손절을 각각 적용**한다(단기 +3%/-2%, 장기 +20%/-10%). 하나의 상수를 공유하면 장기 추천이 단기 기준으로 잘못 알림된다.

### API

`RecommendationOut`에 `track` 필드 추가. `GET /recommendations`는 두 트랙을 함께 반환하고 소비자가 구분한다 — 트랙별 엔드포인트를 나누면 "이번 회차 전체"를 보려는 기존 사용을 깨뜨린다.

### 확률 표시의 정직성 (Unit 2 BR24와 연동)

- 표시 확률은 **겹침 제거 기준**(전체 42.0%, 종목별 26~50%)이다. 겹친 표본의 45.7%를 쓰지 않는다.
- 장기 추천 블록에는 **근거 강도 한 줄**을 함께 적는다: 알트 사이클 표본이 2개뿐이고 out-of-sample 검증이 아니라는 사실. 단기 트랙(5년/876매매)과 같은 신뢰도로 읽히면 안 된다.

## BR25. 4트랙 노출 (2026-08-19) — BR24 대체

- `track` 값이 `ultra | short | mid | long`(BR25 4트랙) 또는 `regime`(기존 레짐 게이트 트랙)이다. **기존 트랙 키를 `short`에서 `regime`으로 바꿨다** -- BR25 '단기'와 목표·손절이 같지만 보유가 24시간 vs 12시간이라 같은 키를 쓰면 감시가 12시간 만에 끊긴다.
- 알림은 하나의 메시지에 **트랙별 섹션 5개**(초단기/단기/중기/장기/기존). 0건이어도 제목을 남겨 어느 트랙이 왜 비었는지 드러낸다.
- 목표가·손절가·청산 기한은 **트랙 스펙에서 유도**한다. 하나의 상수를 공유하면 다른 트랙 값이 전부 틀리게 나간다.
- 가격 감시(BR22)는 가장 긴 트랙(7일) 기준으로 조회하고 보유 기간은 트랙별로 판정한다.
- 국면 문구가 4단계가 되었다: 강세장 / 상승장 / 약상승장 / 상승장 아님.


## BR31 (2026-08-19): 추천 주기 30분 + 중복 알림 억제

### 주기 변경

`CronTrigger(minute=5)` → `CronTrigger(minute="5,35")`. 매시 5분/35분에 실행한다.

**주기를 줄여도 진입 검출이 빨라지지는 않는다.** 진입 신호는 4시간봉이 마감돼야 생기고, 마감 후 5분이면 이미 최단 지연이다. 30분 주기의 실효는 두 가지다:
1. 파이프라인이 실패하거나 지연됐을 때 다음 시도까지의 공백이 절반으로 줄어든다
2. 30분·1시간봉 수집이 더 촘촘해진다

진입 주기 자체를 빠르게 하려면 **진입봉을 30분으로 내려야** 하는데, 실측상 30분봉 진입은 기대수익 -0.00%로 4시간봉(+0.15%)보다 크게 열등하다(BR27 표 참조). 그래서 진입봉은 4시간 유지.

### 중복 알림 억제 (주기 단축의 전제조건)

진입 신호는 **4시간봉 하나**를 가리키는데 파이프라인은 그보다 자주 돈다. 억제가 없으면 같은 추천이 반복 발송된다 -- 실측으로 확인했다:

| 실행(UTC) | 최신 마감 4h봉 | 진입 검출 |
|---|---|---|
| 08-18 16:05 ~ 19:35 (8회) | 08-18 16:00 | **매번 검출** |
| 08-18 20:05 이후 | 08-18 20:00 | - |

시간당 실행에서도 4회, 30분 주기면 **8회 중복**이다.

`recommendations` 테이블의 (market, track, entry_time)을 조회해 이미 알린 조합은 알림에서 제외한다. **저장은 그대로 한다** -- 회차 기록은 남아야 "실행했으나 신호 없음"과 "실행 안 함"을 구분할 수 있다.

조회 범위는 10일이다(가장 긴 트랙 보유 7일보다 넉넉해야 같은 진입봉이 다시 알려지지 않는다).

**검증**: 30분 주기로 8회 실행을 재현한 결과 **검출 8회 → 알림 1회**.


## BR35 (2026-08-19): 역프 알림 — 매수 신호가 아니다

### 무엇을 알리는가

BTC의 한국-해외 가격차가 **-2% 이하**로 내려가면 알린다. 사용자 요청 문턱이다.

```
[시장 이벤트] BTC 역프 -3.12% (기준 -2% 이하)
· 업비트 148,500,000원 / 바이낸스 110,000 USDT (환율 1,394.50)
· 과거 106건 기준 이후 24시간 상승확률 36% (무조건부 52%) — 매수 신호가 아닙니다
```

### 왜 매수 신호로 만들지 않았는가

사용자는 "역프 -2% 이하는 무조건 매수시점"으로 보았으나 **8.9년 실측이 반대를 가리킨다**:

| 문턱 | 사건 | 이후 8h | 이후 24h | 이후 48h |
|---|---|---|---|---|
| -1% | 270 | +0.02% / 47% | +0.20% / 50% | +0.45% / 56% |
| **-2%** | 106 | **-0.20% / 44%** | **-0.50% / 36%** | **-0.31% / 48%** |
| -3% | 37 | -0.12% / 41% | -0.43% / 38% | -0.63% / 49% |
| -4% | 15 | +0.10% / 47% | -0.55% / 40% | +0.94% / 60% |
| -5% | 8 | +0.71% / 38% | +0.41% / 50% | +3.06% / 62% |
| **(무조건부 기저)** | 19,476 | +0.05% / 52% | +0.15% / 52% | **+0.29% / 52%** |

**-2%와 -3%는 기저보다 나쁘다.** 이후 24시간 상승확률이 36~38%로 기저 52%를 크게 밑돈다.

-5%(8건)만 기저를 웃돌지만 표본이 8건이라 BR20-c 기준으로 주장할 수 없고, -4%는 24시간이 -0.55%로 부호가 반대여서 단조성도 없다.

**시기별 재현성도 없다** (-3% 이하 37건의 이후 48시간):

| 연도 | 사건 | 평균 | 상승 |
|---|---|---|---|
| 2018 | 7 | **-4.08%** | 2/7 |
| 2020 | 14 | -0.31% | 7/14 |
| 2021 | 6 | **+4.20%** | 4/6 |
| 2026 | 2 | -7.49% | 0/2 |

2018년과 2021년의 부호가 정반대다.

해석: 역프는 **한국 시장이 먼저 팔린 결과**이므로 하락의 중간이지 끝이 아니다. 그래서 사실만 알리고 매수 판단은 표시하지 않는다.

### 측정 방법 — 환율 기준이 결과를 가른다

프리미엄은 **USD/KRW 실환율**(frankfurter API) 기준이다. 업비트 KRW-USDT로 계산하면 USDT 자체의 한국 프리미엄이 상쇄되어 역프가 구조적으로 작게 나온다:

| 기준 | 기간 | -2% 사건 | 최저 |
|---|---|---|---|
| 업비트 KRW-USDT | 2.2년 | **0건** | -1.37% |
| **USD/KRW 실환율** | **8.9년** | **713건** | **-7.49%** |

**최초 측정이 이 두 가지(환율 기준·기간)를 모두 틀렸다.** 업비트 KRW-USDT 상장(2024-06)에 맞춰 기간을 자른 것이 원인인데, 정작 업비트 KRW-BTC에는 8.9년치가 있었다. 사용자가 "역프 -3%를 겪었다"고 지적해 재검토한 끝에 발견했다.

참고로 정상 구간의 김프 중앙값은 **+1.11%**다 -- 평소엔 한국이 비싸다.

### 상태 전환 시에만 알린다

파이프라인은 30분마다 도는데 역프는 몇 시간씩 이어질 수 있다. 조건이 유지되는 동안 매번 보내면 알림이 쌓이므로, `app_state` 테이블에 직전 상태를 기록해 **역프에 새로 진입할 때 한 번만** 알린다. 정상으로 돌아왔다가 다시 내려가면 다시 알린다.

### 실패 시 동작

환율이나 시세를 못 받으면 **프리미엄을 계산하지 않는다**(추정하지 않는다). 알림이 빠질 뿐 파이프라인은 정상 진행한다.


## BR36 (2026-08-20): 빈 섹션 제거 · 도달 알림 2분 주기 · 트랙별 중복 방지

### 1. 추천이 없으면 섹션을 뺀다

`[단타] [중기] [장기] [기존]` 섹션은 **해당 트랙에 추천이 있을 때만** 표시한다.

BR25에서는 "0건이어도 제목을 남겨 어느 트랙이 왜 비었는지 드러낸다"고 했으나, 실제로는 대부분의 회차가 0건이라 **메시지가 빈 제목으로만 채워졌다.** 국면 문구와 역프 알림은 추천 유무와 무관하게 유지한다.

전부 0건이면 메시지는 헤더 + 국면 문구만 남는다:

```
[coin-recommender] 추천 코인 0개
2026-08-20 09:00 KST

상승장 — BTC·ETH 둘 다 상승 중이지만 강세까지는 아닙니다
· BTCUSDT 약상승:  일 +0.3%  주 +1.8%  ...
```

### 2. 도달 알림은 이미 별도다 (확인)

손절가·매도가·진입가 도달 알림은 **추천 알림과 완전히 분리된 메시지**이며 별도 스케줄로 돈다(BR22). 요청과 현행이 이미 일치했다.

여러 도달이 동시에 발생해도 **메시지는 하나**다 -- 종목마다 따로 보내면 알림이 쌓인다.

### 3. 감시 주기 5분 → 2분

`CronTrigger(minute="*/2")`. 활성 추천이 없으면 조회 없이 즉시 끝나므로 추천이 없는 동안의 비용은 사실상 없다.

### 4. 트랙별 중복 방지 — 결함 수정

`mark_price_event`가 `(run_time, market)`만 보고 있었다. **`track`이 빠져 있어**, 같은 종목이 단타(+2%)·중기(+5%)·장기(+10%)에 동시에 뽑힌 경우 **단타 목표 도달이 나머지 두 트랙까지 "알림 완료"로 표시**했다. 그 트랙들의 도달은 영영 알려지지 않는다.

BR32에서 `recommendations` PK를 `(run_time, market, track)`으로 넓히면서 이 UPDATE만 따라가지 못한 것이다.

`WHERE ... AND track = ?`를 추가하고, `PriceEvent`에 `track`을 실어 알림 문구에도 어느 트랙의 도달인지 표시한다:

```
[coin-recommender] 가격 알림 2건
(1) SOLUSDT · [단타] 매도가 도달
· 매도가: 78.54  (+2%)
(2) SOLUSDT · [장기] 매도가 도달
· 매도가: 84.7  (+10%)
```

같은 (종목, 트랙, 이벤트)는 여전히 **최초 1회만** 나간다 -- 기록 컬럼이 곧 중복 방지 장치다.


## BR37 (2026-08-20): 실제 운영 실적 표시 + 중복 저장 차단

### 무엇을 표시하는가

**실제로 발송한 추천**이 매도가에 도달한 비율. 백테스트 확률과 별개 수치다.

```
[실적] 매도가 도달 12/14건 = 86% — 표본 14건, 아직 판단하기 이릅니다
· 단타 88%(8건)  중기 83%(6건)
```

표본이 30건 미만이면 "아직 판단하기 이릅니다"를 붙인다. 트랙 실측 도달률이 19~37%인데 표본 20건이면 우연히 86%가 나올 수 있고, **실제로 첫날 14건에서 86%가 나왔다.**

결과가 확정된 것(매도가 또는 손절가 도달)만 센다 -- 진행 중인 건을 넣으면 BR24에서 겪은 "미완료 매매를 타임아웃으로 집계" 결함이 반복된다.

### 중복 저장 차단 (3중)

`(종목, 트랙, 진입봉)`이 곧 하나의 추천이다. 파이프라인이 30분마다 돌면서 같은 4시간봉 진입을 반복 저장하고 있었다 -- **원시 118행 = 고유 진입 17건**으로 7배 부풀었다.

1. **저장 단계**: `save_run`이 알림에서 걸러진 것(`fresh_*`)만 저장한다. 회차 기록은 `pipeline_runs`가 담당하므로 중복 행은 아무것도 더하지 않는다.
2. **DB 레벨**: `(market, track, entry_time)` 유니크 인덱스 + `INSERT OR IGNORE`. 애플리케이션 중복 제거가 실패해도 막히며, 예외가 아니라 조용히 무시된다.
3. **집계 단계**: `get_live_performance`가 방어적으로 `GROUP BY market, track, entry_time`을 쓴다.

### 데이터 복구 (1회성)

BR36 이전 기록은 `mark_price_event`가 track을 무시해 오염돼 있었다. 실제 1분봉으로 트랙별 목표·손절을 전수 재판정한 결과 **3건이 잘못 기록**돼 있었다:

| 종목 | 트랙 | 기존 | 실제 |
|---|---|---|---|
| AVAX | 장기 | 목표 도달 | **미결** |
| AVAX | 중기 | 목표 도달 | **미결** |
| XPL | 중기 | 목표 도달 | **미결** |

검증 예: AVAX 진입 6.56, 도달 기록 시각의 1분봉 고가 6.761 → 단타 목표 6.6912 도달 O / 중기 6.888 미달 / 장기 7.216 미달인데 셋 다 도달로 기록됐다.

복구 후 실적 15/17(88%) → **12/14(86%)**. 이어서 중복 103행을 삭제해 **17행 = 고유 진입 17건**으로 정리했다(실적 수치는 불변).

### 매수가는 진입봉 종가 유지

종가보다 낮은 지정가로 들어가는 안을 측정했다. 미체결(4시간 안에 그 가격이 안 오면 포기)을 정직하게 반영하면:

| 매수가 | 체결률 | 도달률(단타) | 신호당 기대(단타) | 신호당 기대(장기) |
|---|---|---|---|---|
| **종가** | 99% | 36.9% | **+0.09%** | **+0.67%** |
| 종가 -0.5% | 72% | 37.7% | +0.05% | +0.46% |
| 종가 -1.0% | 50% | 40.1% | +0.04% | +0.32% |
| 종가 -2.0% | 23% | 46.3% | +0.03% | +0.23% |

**싸게 사면 도달률은 오르지만**(36.9% → 46.3%) **체결이 절반 이하로 줄어 신호당 기대수익은 떨어진다.** 가격이 안 내려온 신호가 가장 잘 가는 신호이기 때문이다 -- 눌림을 기다리면 그것들을 통째로 놓친다.


## BR38 (2026-08-20): 가격 알림 병합 + 트랙별 비율 표기 수정

### 결함 1 — 손절·목표 비율이 기존 트랙 상수로 하드코딩돼 있었다

`_EVENT_LABELS`가 모듈 로드 시점에 `TARGET_RETURN`(3%)·`STOP_LOSS`(2%)로 문자열을 만들어 두고 있었다. **트랙마다 목표·손절이 다른데 전부 같은 값으로 표기**됐다:

```
(4) ACEUSDT · [중기] 손절가 도달
· 손절가: 0.190272  (-2%)      <- 가격은 -4%인데 표기만 -2%
```

가격 자체는 트랙 스펙에서 계산돼 맞았고 **표기만 틀렸다.** BR32에서 트랙별 손절을 도입할 때 이 상수만 따라가지 못했다.

수정: `_event_note(kind, track)`가 트랙 스펙에서 비율을 가져온다. 스펙에 없는 키(`regime`)는 기존 상수로 떨어진다.

### 결함 2 — 진입가 알림이 트랙마다 중복

진입가는 **트랙과 무관하게 같은 값**(진입봉 종가)이다. 그런데 트랙별로 행이 나뉘어 있어 같은 내용이 2~3번 알림됐다:

```
(1) ACEUSDT · [단타] 진입가 도달 ... 0.1982
(2) ACEUSDT · [중기] 진입가 도달 ... 0.1982   <- 같은 내용
```

수정: `_merge_events`가 **(종목, 종류, 가격)이 같으면 하나로 합치고** 관련 트랙을 함께 표시한다. 목표·손절은 트랙마다 값이 다르므로 자연히 합쳐지지 않는다.

### 수정 후

```
[coin-recommender] 가격 알림 3건

(1) ACEUSDT · [단타] [중기] 진입가 도달 (지금 진입 가능)
· 진입가: 0.1982  (기준)

(2) ACEUSDT · [단타] 손절가 도달
· 손절가: 0.194236  (-2%)

(3) ACEUSDT · [중기] 손절가 도달
· 손절가: 0.190272  (-4%)
```

4건 → 3건으로 줄고, 각 손절 비율이 실제 값과 일치한다.

## BR39 (2026-08-20): 판정 주체를 감시 기록 하나로 통일

**문제**: 추천 결과 판정이 **두 곳에서 서로 다른 규칙으로** 돌고 있었다.

| | 판정 주체 | 목표/손절 | 보유기간 | 사용 봉 |
|---|---|---|---|---|
| 감시 (BR22, 2분 주기) | `monitor.check_price_events` | **트랙별** (+2/+5/+10%, -2/-4/-5%) | **트랙별** 8/24/48h | 1분봉 |
| 실적 (구 BR11) | `backtest.evaluate_outcome` | 레거시 고정 +3% / -2% | 고정 24h | 1시간봉 |

같은 추천에 대해 감시는 "단타 +2% 도달", 실적은 "+3% 미달 실패"로 기록될 수 있었다. BR32에서 트랙별 파라미터를 도입할 때 감시 경로만 고치고 실적 경로가 남은 것으로, `mark_price_event`(BR36)·`_EVENT_LABELS`(BR38)에 이은 **같은 계열 3번째 누락**이다.

DB 확인 결과 `target_reached`가 전부 NULL이어서 잘못된 값이 쌓이지는 않았다 — 판정이 아예 동작하지 않고 있었다.

**규칙**: 결과 판정의 권위는 **감시 기록 하나뿐**이다. `pipeline.evaluate_pending_outcomes`는 다시 판정하지 않고 감시 기록에서 **유도**한다.

- `target_hit` 기록 있음 → 성공, 실현수익 `+spec.target`
- `stop_hit` 기록 있음 → 실패, 실현수익 `-spec.stop`
- 둘 다 없고 `entry_time + spec.hold_hours` 경과 → 마감 시각 종가로 실현수익 계산, 미도달
- 아직 보유 기간 내 → 판정 보류

**제거**: `backtest.evaluate_outcome`, `RecommendationOutcome`, `data_store.record_outcome` — 이 변경으로 호출자가 사라진 고아 코드.

## BR40 (2026-08-20): 만료도 트랙별 보유기간을 따른다

`/recommendations`의 `_is_expired`가 **회차 단위로 24시간**을 일괄 적용하고 있었다. BR32 트랙 파라미터화의 잔재로, 결과는:

- **장기(48h)**: 마감 24시간 전에 응답에서 사라짐 — 아직 유효한 추천이 소멸
- **단타(8h)**: 마감 후 16시간을 더 살아 있음 — 끝난 추천이 유효한 것처럼 노출

`_to_recommendation_out`이 이미 트랙별 `exit_deadline`을 계산하고 있으므로, 만료는 그 값으로 판정한다(`_live_recommendations`). `entry_time`이 없는 옛 행만 기존 회차 단위 24시간을 적용한다.

`expired` 플래그는 살아남은 추천이 하나도 없을 때만 회차 기준으로 세운다 — 한 트랙만 마감된 상황을 "회차 전체 만료"로 표시하지 않는다.

## BR42 (2026-08-20): 가격 표기 — 지수 표기 제거, 바이낸스 호가 단위 복원

**문제**: 모든 가격이 `f"{v:,.6g}"`로 표기돼 있었다. `%g`는 두 방향으로 망가진다.

| 값 | 표기 | 문제 |
|---|---|---|
| PEPE 매도가 3.157e-06 | `3.157e-06` | **지수 표기** — 읽을 수 없다 (실제 발송됨) |
| BTC 118432.15 | `118,432` | 유효숫자 6자리에서 잘려 **소수점 소실** |
| ACE 손절가 0.194236 | `0.194236` | 바이낸스 호가보다 과한 자릿수 |

**소수 자릿수 고정은 답이 아니다.** 6자리로 반올림하면 PEPE 진입가 0.00000287과 매도가 0.00000316이 **둘 다 `0.000003`**이 되어 진입가와 매도가의 구분 자체가 사라진다. 단가가 작은 종목일수록 정확히 그 종목에서 깨진다.

**규칙**: **소수 8자리에서 내림**하고 꼬리 0을 뗀다 (최소 2자리).

```
Decimal(f"{v:.10g}").quantize(Decimal("1e-8"), rounding=ROUND_FLOOR)
```

8자리인 근거: 바이낸스 USDT 현물 484종의 호가 단위(`PRICE_FILTER.tickSize`)를 전수 조사한 결과 **0~8자리이고 최대가 8자리**다(4자리 152종 / 5자리 127 / 2자리 95 / 3자리 59 / 6자리 32 / 8자리 11 / 7자리 4 / 1자리 3 / 0자리 1). 가장 잘게 쪼개는 종목에 맞추면 어느 종목도 잘리지 않는다.

**자르기 전에 유효숫자 10자리로 정리하는 이유**: 목표·손절가는 곱셈으로 만들어져 부동소수점 오차를 달고 있다. `6.56 * 1.02`는 6.6911999999999995이고, 이대로 8자리에서 내리면 **`6.69119999`**가 되어 고치기 전보다 더 깨져 보인다. 실측에서 AVAX 매도가 `6.69119999`, ADA 손절가 `0.17590999`, ACE 매도가 `0.20216399`가 그렇게 나왔다.

**내림을 쓰는 이유**: 표시된 매도가가 실제 목표보다 높으면 그 지정가는 체결되지 않는다.

**남은 제약**: 목표·손절가는 파생값이라 종목별 호가 단위에 딱 떨어지지 않는다 -- 실측상 30종 중 22종에서 호가보다 1~2자리 길다(예: SOL 매도가 89.649, 호가 단위 0.01). 지정가 주문 시에는 해당 종목 호가로 맞춰야 한다. 종목별 `tickSize` 반올림은 `exchangeInfo` 의존이 생겨 채택하지 않았다.

**검증** (실제 저장된 추천 20건 전수)

| 종목 | 항목 | 수정 전 | 수정 후 |
|---|---|---|---|
| PEPE | 진입가 | `2.87e-06` | `0.00000287` |
| PEPE | 매도가(장기) | `3.157e-06` | `0.00000315` |
| PEPE | 손절가(장기) | `2.7265e-06` | `0.00000272` |
| AVAX | 매도가(단타) | `6.6912` | `6.6912` |
| XRP | 매도가(중기) | `1.05599` | `1.055985` |

- 지수 표기 **0건**
- 저장된 추천 20건의 진입·매도·손절 60개 값에서 지수 표기 및 8자리 초과 **0건**
- PEPE 세 값(진입/매도/손절)이 모두 다른 문자열로 표시됨

적용 지점: 추천 알림의 진입가·매도가·손절가, 가격 도달 알림, 역프 알림의 바이낸스 가격.
