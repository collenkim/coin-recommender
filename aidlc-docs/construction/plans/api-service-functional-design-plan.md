## 사전 결정 사항 (질문 없이 확정 — 근거 명시)

| 항목 | 결정 | 근거 |
|---|---|---|
| 추천 결과 영속화 | `DataStore`에 `pipeline_runs`(run_time, regime_bullish) + `recommendations`(run_time, market, expected_return, n, hit_count) 2개 테이블 신설 | FR11이 서비스 재시작 후에도 "최신 추천"을 조회 가능해야 함(요구사항엔 없었지만 GET 엔드포인트의 당연한 기대치) + FR10에서 0개 추천이 정상 케이스이므로, "실행은 했으나 결과 0개"와 "아직 한 번도 실행 안 함"을 구분하려면 실행 자체를 기록하는 테이블이 별도로 필요 |
| 텔레그램/디스코드 동시 지원 | `.env`에 설정된 웹훅 URL마다 각각 발송 (하나만 설정되면 하나만, 둘 다 설정되면 둘 다) | 원 스펙이 "텔레그램/디스코드 웹훅"이라고 병기했고, 양자택일보다 "설정된 채널 모두 발송"이 가장 자연스럽고 유연한 해석 — 별도 질문 없이도 명백함 |
| 동시 실행 방지 | 프로세스 내 락(in-process lock)으로 파이프라인 중복 실행 방지 — 이미 실행 중이면 `POST /run`은 즉시 "이미 실행 중" 응답 반환 | 스케줄러 실행과 수동 `POST /run`이 겹칠 수 있는데, 중복 실행은 낭비이고 동시 DB 쓰기 경합 위험도 있음 — 표준적이고 저비용인 방어 |
| 알림 발송이 파이프라인 결과 저장을 막지 않음 | 웹훅 전송 실패해도 추천 결과는 이미 저장됨, 알림은 best-effort | RESILIENCY-10(우아한 성능 저하)과 일관 — 알림은 부가 기능이지 핵심 데이터 경로가 아님 |
| 알림 메시지 언어/형식 | 한국어, 코인별로 "마켓 — 기대수익률 X% (과거 N회 중 M회 적중)" 형식, 추천 0개면 "이번 회차 추천 없음" | 대화가 한국어로 진행됐고, 스펙 예시("기대수익률 5.1% (과거 3회 중 2회 적중)")를 그대로 따름 |

질문 없이 바로 산출물을 생성합니다. 알림 형식 등 사소한 부분은 Request Changes로 언제든 조정 가능합니다.
