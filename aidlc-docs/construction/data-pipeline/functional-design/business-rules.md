# Business Rules — Unit 1: data-pipeline

## BR1. 후보군 필터
- KRW 마켓만 대상
- BTC, ETH 마켓 코드는 항상 제외
- 24시간 거래대금 기준 상위 20개만 후보로 선정

## BR2. 부트스트랩 최소 캔들 수
- 지표 계산용으로 최소 100봉 필요 (스팬B 52 + 선행이동 26 + 여유분 고려)
- 100봉 미만이면 해당 (market, timeframe)은 이번 회차에서 스킵 (신규 상장 등으로 이력 부족 시)

## BR3. 백테스트용 이력 수집
- `backtest_lookback_days` (기본 **5840일 = 16년**, `config/settings.yaml`에서 설정 가능) 만큼 추가 수집. 상한값이며 실제로는 거래소 가용 최대까지만 받는다 (바이낸스 BTCUSDT 최초봉 2017-08-17 = 약 9년)
- 지표용 100봉 수집과 동일한 upsert 대상 — 별도 로직/테이블 불필요

## BR4. 증분 수집 기준
- (source, market, timeframe)별 저장된 마지막 `candle_time` 이후 캔들만 조회
- 저장 이력이 없으면 BR2/BR3 적용 (부트스트랩)
- 저장 이력이 있으나 설정된 lookback보다 얕으면 증분에 더해 BR11 소급 백필 수행

## BR5. Upsert 유일성
- 유니크 키: (source, market, timeframe, candle_time)
- 동일 키로 재수집 시 값 갱신 (거래소가 진행 중 캔들을 보정하는 경우 대응)

## BR6. 타임스탬프 정규화
- 모든 `candle_time`은 UTC로 정규화해 저장 (업비트/바이낸스 소스 간 일관성 확보)

## BR7. 부분 실패 격리
- 특정 마켓의 수집이 실패(네트워크 오류, API 오류 등)해도 예외를 전체 파이프라인으로 전파하지 않고, 해당 마켓만 건너뛰고 나머지는 계속 처리 (RESILIENCY-10 graceful degradation)
- Binance BTC/ETH 수집 실패는 레짐 판정 자체가 불가능해지므로 Unit 2(Scorer)가 안전하게 빈 추천으로 처리 (Unit 1은 실패 사실만 전달)

## BR8. 바이낸스 후보군 필터 (신규 — 거래소별 추천 5개씩 요청, Requirements FR-B1)
- USDT 마켓만 대상 (기존 BTCUSDT/ETHUSDT 참조 종목과 동일한 견적통화 — 유동성/데이터 일관성)
- BTC, ETH(USDT) 마켓 코드는 항상 제외 (레짐 참고용으로만 사용, 추천 후보 아님 — BR1과 동일 원칙)
- **스테이블코인 페어 제외** (Requirements Q1): base 자산이 스테이블코인인 페어(예: USDCUSDT, FDUSDUSDT, TUSDUSDT, DAIUSDT, USDPUSDT 등)는 모멘텀 신호와 무관하므로 제외
- **레버리지/파생 토큰 제외** (Requirements Q1): base 심볼이 `UP`/`DOWN`/`BULL`/`BEAR`로 끝나는 페어(예: BTCUPUSDT) 제외
- 24시간 거래대금(quoteVolume) 기준 상위 20개만 후보로 선정 (BR1과 동일 개수, `top_n_candidates` 설정 재사용)

## BR9. 바이낸스 후보 코인 캔들 수집 (신규 — Requirements FR-B2)
- BR8로 선정된 각 바이낸스 후보 코인에 대해 1시간봉/4시간봉을 수집한다 (기존에는 BTC/ETH 4시간봉만 수집했음 — 1시간봉 골든크로스 시그널 계산에 필요하므로 신규 추가)
- 부트스트랩/증분/upsert/타임스탬프 정규화/부분 실패 격리 규칙은 BR2~BR7과 완전히 동일 (source="binance"로 동일한 `DataStore` 메서드 재사용, 신규 저장 로직 불필요)

## BR10. 바이낸스 이력 페이지네이션 및 백필 (신규 — 2026-08-10 버그 수정, Requirements FR-R1)

**발견된 결함**: Binance `/api/v3/klines`는 응답당 최대 1,000개만 반환하는데 `BinanceClient.get_klines`가 `min(limit, 1000)`으로 조용히 잘라내고 페이지네이션이 없었습니다. 그 결과 `backtest_lookback_days: 180`(1시간봉 4,320개) 설정이 **무시되고 실제로는 1,007봉(41일)만 저장**되고 있었습니다. 업비트는 pyupbit가 내부적으로 페이지네이션하므로 4,415봉(184일)이 정상 저장되어, 두 거래소의 표본 규모가 4.5배 어긋나 있었습니다.

**규칙**:
- 목표 시작 시각 = `지금 - backtest_lookback_days`
- 저장된 **최초** 캔들 시각(`get_first_candle_time`)이 없거나 목표 시작 시각보다 늦으면 → `get_klines_since()`로 목표 시작 시각부터 페이지네이션 수집(백필). 요청당 1,000개씩 앞으로 진행하며, 짧은 페이지가 오면 종료. 폭주 방지 상한 20회 요청(=20,000봉)
- 이력이 이미 충분하면 → 기존 증분 수집(마지막 캔들 이후만)
- 백필은 **증분 경로로는 절대 채워지지 않는다**는 점이 핵심입니다. 증분은 앞으로만 진행하므로, 이미 1,007봉이 저장된 마켓은 영원히 과거를 못 채웁니다. 그래서 "마지막 캔들"이 아니라 "최초 캔들" 기준으로 판단합니다.

**실측 결과**: 1,007봉(41일) → 4,320봉(180일). 재실행 시 증분 경로로 전환되어 반복 백필 없음. 후보 20개 + BTC/ETH 전체 백필에 약 13초, `POST /run` 1회 전체가 50초.

**알려진 비용 (수용)**: 상장이 lookback 기간보다 최근인 코인은 `최초 캔들 <= 목표 시작 시각`을 영원히 만족할 수 없어 매 실행 자신의 (짧은) 이력을 재수집합니다. 시간당 요청 몇 건 수준으로 Binance 공개 API 레이트리밋 내에 충분히 들어와 별도 상태 저장 없이 단순하게 두었습니다.

## BR11. 업비트 이력 소급 백필 및 lookback 1년 확대 (신규 — 2026-08-11, Requirements FR-Y1/FR-Y2)

**배경**: `backtest_lookback_days`를 180 → **365**로 올렸습니다. 그런데 업비트 수집은 부트스트랩 판정을 `get_last_candle_time is None`(= DB가 비었을 때)으로만 하고 있어서, 이미 180일치가 저장된 마켓은 증분 경로로만 들어가고 **설정을 올려도 영원히 180일에 머무릅니다**. 증분은 앞으로만 진행하기 때문입니다(BR10과 동일한 구조적 문제). 즉 백필 없이 설정값만 바꾸면 변경이 바이낸스에만 적용됩니다.

**규칙**:
- 목표 시작 시각 = `지금 - backtest_lookback_days`
- 저장된 **최초** 캔들(`get_first_candle_time`)이 없으면 → 목표 시작 시각까지의 전체 봉 수를 부트스트랩 수집
- 최초 캔들이 있고 목표 시작 시각보다 늦으면 → **증분 수집 + 부족한 과거 구간만 소급 수집**(`to=최초 캔들 시각`)
- 이력이 충분하면 → 증분 수집만

**바이낸스(BR10)와 다른 점 — 백필 범위**: 바이낸스는 백필 시 `목표 시작 시각 ~ 현재` 전체를 다시 받지만, 업비트는 **비어 있는 과거 구간만** 요청합니다. 이유는 두 가지입니다. (1) 업비트는 요청당 200봉(바이낸스는 1,000봉)이라 전체 재수집 비용이 5배입니다. (2) 상장이 lookback보다 최근인 코인은 `최초 캔들 <= 목표 시작 시각`을 영원히 만족할 수 없어 매 실행 이 분기를 타는데(BR10의 "알려진 비용"), lookback이 1년이 되면 해당 코인 수가 크게 늘어납니다. 과거 구간만 요청하면 이 상시 비용이 요청 수십 건이 아니라 **타임프레임당 1건**으로 묶입니다.

**실측 결과** (운영 DB 사본, 실제 업비트/바이낸스 호출):

| 항목 | 변경 전 | 변경 후 |
|---|---|---|
| KRW-ADA 1시간봉 | 4,327봉 (180일) | **8,752봉 (365일)** |
| KRW-ADA 4시간봉 | 1,081봉 | **2,190봉** |
| BTCUSDT/ETHUSDT 4시간봉 | 1,080봉 | **2,189봉** |
| 백필 1회 비용 (KRW-ADA) | — | 30 요청 / 4.4초 (1회성) |
| 정상 상태 재실행 비용 | 2 요청 | **2 요청** (변화 없음) |
| 상장이 1년 미만인 코인 (KRW-BLEND) | — | 매 실행 **4 요청** (전체 재수집이었다면 26 요청) |

**레짐 기준 종목도 함께 깊어져야 함**: 백테스트 표본은 `_regime_bullish_at`(BTC/ETH 4시간봉)을 통과해야 채택되는데, `as_of`는 기준 종목 이력보다 이전 시점에 대해 None을 돌려줍니다. 따라서 BTC/ETH 4시간봉이 180일에 머무르면 새로 확보한 업비트 과거 봉이 **전부 기각**됩니다. 실측: KRW-ADA 표본수 n=2 (BTC/ETH 180일) → **n=13** (BTC/ETH 365일). BTC/ETH는 BR10 백필이 동일한 `backtest_lookback_days`를 쓰므로 자동으로 함께 확대됩니다.

**성능**: 이력이 2배가 되어도 코인당 이치모쿠 계산 0.56초 + 백테스트 스캔 0.04초 (8,752봉 기준). 40개 코인 환산 약 24초로 매시 실행 창 안에 들어옵니다. 스캔이 봉 수에 선형인 이유는 `as_of` 선형 탐색이 골든크로스가 발생한 봉에서만 호출되기 때문입니다(전체 봉의 약 2%).

**DB 크기**: 33MB → 약 66MB 예상 (SQLite, 캔들 2배).

## BR12. 바이낸스 전용 수집 (2026-08-11)

추천이 바이낸스 전용이 되면서 업비트 수집을 제거했습니다. 업비트 캔들은 업비트 추천에만 쓰였고 다른 소비자가 없었으므로, 남겨두면 매 실행 순수 낭비입니다. 누적 업비트 추천이 0건이라 미평가 이력도 없어 제거가 안전했습니다.

`UpbitClient` / `MarketSelector` 모듈 자체는 남겨두었습니다 — 되살릴 때 재작성이 아니라 파이프라인 3줄 복원으로 끝나도록 하기 위함입니다. 현재 운영 경로에서는 호출되지 않습니다.

**후보 코인의 4시간봉 수집도 제거**했습니다. 새 진입 조건(BR19)이 1시간봉만 쓰므로 4시간봉은 소비자가 없습니다. BTC 4시간봉은 레짐 판정(BR20)에 필요하므로 계속 수집합니다.

**알려진 제약**: 거래대금 상위 20개는 신규 상장 비중이 큽니다. 실측(2026-08-11) 결과 바이낸스 20개 중 4개가 이력 부족(SPCXB 1,423봉, SNDKB 1,446봉, RLUSD n=1, PAXG 0봉)으로 표본 하한 n>=3을 채울 수 없습니다. lookback을 늘려도 코인이 존재하지 않던 기간은 채워지지 않으므로 구조적 한계입니다.

## BR28 (2026-08-19): 거래소 최초봉 캐시 — 반복 요청 절반으로

### 문제

`_collect_and_store_binance`는 매 실행마다 조합(종목 × 타임프레임)당 **2요청**을 썼다:
1. "거래소가 줄 수 있는 가장 오래된 봉" 확인 (BR25에서 추가한 절단 방지 장치)
2. 증분 수집

후보 30종 × 7개 봉 = 210조합이므로 **시간당 424요청**이었다. 그런데 **거래소 최초봉은 한 번 확인하면 바뀌지 않는 값**이다 -- 매번 물어볼 이유가 없다.

### 해결

`collection_state` 테이블에 (source, market, timeframe) → exchange_earliest를 캐시한다. 캐시가 있으면 조회 없이 판단하고, 없을 때만 1요청을 쓴다.

**실측**: 405요청/37초 → **210요청/18초**. 조회 실패 시에는 여전히 백필로 떨어진다(판단이 틀려 수집을 건너뛰는 것보다 한 번 더 받는 쪽이 안전).

### 데이터 확보 현황 (2026-08-19)

**후보 30종 전부 상장일까지 완전 확보**되어 있다. 미확보 0종.

| 봉 | 평균 보유 | 최대 | 제한 요인 |
|---|---|---|---|
| 15m | 2.6년 | 8.8년 | **인위적 상한 2년** (미사용 봉) |
| 30m | 3.3년 | 8.8년 | 상장일 |
| 1h | 2.6년 | 8.8년 | 상장일 |
| 4h | 2.8년 | 8.8년 | 상장일 |

**"9년치"는 오래된 종목만 가능하다** -- BNB 8.8년, ADA/XRP 8.3년이 최대이고 2025~2026 상장 종목(SNDKB, SPCXB, KORUB 등)은 구조적으로 1년 미만이다. 평균이 2.6~3.3년인 것은 후보에 최근 상장 종목이 많기 때문이지 설정 제약이 아니다.

### DB 크기

현재 **779MB / 531만 봉** (봉당 약 147바이트).

15분봉 상한(2년)을 풀어 9년으로 받으면 **+605만 봉 / +0.89GB → 약 1.67GB**가 된다. **어느 트랙도 15분봉을 쓰지 않으므로**(진입 4h · 판정 30m) 상한을 유지한다. 필요해지면 `LOOKBACK_DAYS_BY_TIMEFRAME`에서 한 줄 지우면 된다.

## BR29 (2026-08-19): 새 봉이 없으면 조회하지 않는다

### 문제

BR28에서 최초봉 확인을 캐시해 424 → 210요청으로 줄였지만, 남은 210요청도 상당수가 **"변화 없음"을 확인하는 데만** 쓰이고 있었다. 주봉은 주 1회, 월봉은 월 1회만 새 봉이 생기는데 **매시간 물어보고 있었다.**

### 해결

마지막 저장 봉의 **다음 봉이 마감될 시각**을 계산해, 아직이면 조회 자체를 건너뛴다. 이력이 없으면 수집한다.

| 봉 | 봉 길이 | 시간당 조회 필요 |
|---|---|---|
| 15m | 0.25h | 100% |
| 30m | 0.5h | 100% |
| 1h | 1h | 100% |
| 4h | 4h | **25%** |
| 1d | 24h | **4%** |
| 1w | 168h | **1%** |
| 1M | 720h | **0.1%** |

**실측**: 직후 재실행 시 **13요청 / 3초** (BR28 적용 후 210요청 / 18초). 정상 시간당 운영은 약 99요청으로 수렴한다.

누적 개선: **424 → 210(BR28) → 약 99(BR29)요청/시간.**

### 15분봉을 쓰지 않는 이유 (정정)

"효과가 없어서"가 **아니다.** 역할별로 결과가 갈린다:

**진입봉으로서는 확실히 나쁘다** (골든크로스 · 판정 30m):

| 진입봉 | 초단기 | 단기 | 중기 | 장기 |
|---|---|---|---|---|
| 30m | -0.00% | +0.01% | +0.04% | +0.14% |
| 1h | +0.02% | +0.02% | +0.01% | +0.25% |
| **4h** | **+0.15%** | **+0.22%** | **+0.26%** | **+0.56%** |
| 1d | +0.09% | +0.10% | +0.06% | +0.49% |

**판정봉으로서는 오히려 30분봉보다 나았다**:

| 판정봉 | 표본 | 도달률 | 기대수익 |
|---|---|---|---|
| 1h | 1,271 | 34.1% | +0.12% |
| **30m** | 1,270 | 34.7% | +0.15% |
| **15m** | **822** | **41.2%** | **+0.18%** |

15분봉 판정이 수치는 가장 좋지만 **표본이 35% 적다** -- 이력 상한을 2년으로 두었기 때문이다. 표본이 적은 쪽 수치를 채택할 근거가 약해 30분봉을 골랐다.

**즉 "효과가 없다"가 아니라 "이력을 얕게 받아 공정 비교가 안 된다"가 정확한 이유다.** 15분봉을 9년으로 받으면(+605만 봉 / +0.89GB → DB 약 1.67GB) 공정 비교가 가능하고, 그때 판정봉을 15분으로 내릴지 다시 판단할 수 있다. 미측정 상태로 남겨 둔다.

## BR30 (2026-08-19): 15분봉 상한 해제 중 발견한 데이터 구멍

### 15분봉 2년 상한 해제

`LOOKBACK_DAYS_BY_TIMEFRAME` 전체를 제거했다 -- 이제 모든 타임프레임이 설정값(16년 상한, 실제는 거래소 가용 최대)을 쓴다. `_MAX_PAGES` **300 → 600** (16년치 15분봉 561페이지).

### 발견: 데이터에 구멍이 있었다

15분봉을 채우다 **BNBUSDT 15분봉이 2022-05에서 멈춰 있는 것**을 발견했다. 연도별 봉 수:

| 연도 | 봉 수 | 충족률 |
|---|---|---|
| 2017 | 5,355 | 15% (11월 상장) |
| 2018~2021 | 34,778~35,053 | 99~100% |
| 2022 | 13,758 | **39%** |
| 2023~2026 | **0** | **0%** |

**최초봉(2017-11)과 최신봉이 모두 정상으로 보여 "완료"로 판정되고 있었다.** 앞뒤만 보고 가운데를 보지 않은 것이다.

### 원인 — 증분 경로가 1회 1,000봉 상한

`get_klines(start_time=last_time, limit=1000)`은 **1회 1,000봉**이 상한이다. 15분봉이면 **10일치**뿐이다. 4년 뒤처진 타임프레임은 따라잡는 데 약 150회 실행이 필요하고, 그동안 데이터에 구멍이 남는다.

초기 수집이 `_MAX_PAGES=150`에서 잘려 2022년까지만 채워졌고, 그 뒤로는 증분이 매 실행 10일씩만 전진하고 있었다.

### 수정

증분도 `get_klines_since`(페이지네이션)를 쓴다. 최신 상태면 짧은 페이지를 만나 **1요청으로 끝나므로 정상 상태의 비용은 같고**, 뒤처졌을 때만 따라잡는다.

이로써 절단 계열 결함의 **네 번째**다(BR25 20페이지 → 2.3년, BR27 15분봉 316페이지, BR28 30분봉 3년 상한, BR30 증분 1,000봉). 공통 교훈: **"최초봉이 있으니 완료"로 판단하면 안 된다.**


### 공정 비교 결과 — 판정봉은 30분 유지

구멍을 메워 15분/30분/1시간봉이 **모두 같은 표본(2,115건)**이 된 뒤 다시 비교했다:

| 트랙 | 판정 1h | 판정 30m | 판정 15m |
|---|---|---|---|
| 초단기 | +0.11% | **+0.13%** | **+0.13%** |
| 단기 | +0.21% | **+0.22%** | **+0.22%** |
| 중기 | +0.25% | +0.25% | +0.25% |
| 장기 | +1.18% | +1.18% | +1.18% |

**15분봉과 30분봉의 차이가 사라졌다.** 이전 비교에서 15분봉이 우세해 보였던 것(+0.18% vs +0.15%)은 **표본이 35% 적고 최근 구간에 치우쳐 있었기 때문**이지 해상도 자체의 효과가 아니었다. 1시간봉만 초단기·단기에서 약간 열등하다(판정 봉수가 8개로 적어 손실 편향이 남는다).

**판정봉은 30분을 유지한다.** 15분봉은 같은 성능에 저장량만 2배다(15분봉 단독 약 300만 봉).

15분봉 이력을 9년으로 받은 것은 **이 비교를 공정하게 만들기 위해서였고, 그 목적은 달성했다.** 결과가 "차이 없음"이라는 것도 측정으로 확인된 답이다.


## BR33 (2026-08-19): 신규 상장 종목을 후보에서 제외

### 거래량 측정 기준 (재확인)

`quoteVolume` = **24시간 거래대금(USDT 환산)**을 쓴다. 코인 개수가 아니라 금액 기준이라 종목 간 비교가 성립한다. 후보는 `symbol.endswith("USDT")`로 걸러 **USDT 페어만** 대상이다.

### 문제

거래량 상위권에 상장 직후 종목이 자주 올라온다. 이력이 없어 표본을 만들 수 없으므로 **추천이 원천 불가한데 슬롯만 차지한다.**

2026-08-19 실측, 상위 30 슬롯:

| 종목 | 상장 경과 | 단타 표본 | 중기 | 장기 |
|---|---|---|---|---|
| SNDKB | 0.2년 | 3 | 3 | 1 |
| SPCXB | 0.2년 | 4 | 3 | 2 |
| SNXXB | 0.1년 | 1 | 1 | 0 |
| SKHYB | 0.1년 | 3 | 3 | 1 |
| KORUB | 0.1년 | 2 | 2 | 2 |
| SOXLB | 0.1년 | 2 | 2 | 1 |
| MUB | 0.2년 | 4 | 4 | 3 |

표본 하한이 10건이므로 **7종 전부 통과 불가**였다. 상위 30 중 23종만 실제로 쓸 수 있었다.

(참고: 이들은 24시간 거래되고 봉 결손도 없다 -- 존재율 100%. 문제는 거래 방식이 아니라 이력 길이다.)

### 해결

**상장 후 180일 미만이면 후보에서 제외**하고, 그 자리를 다음 순위가 채운다.

6개월로 잡은 근거: 종목당 골든크로스가 연 41회(실측)이므로 6개월이면 약 20회가 쌓여 표본 하한 10건을 넘긴다.

**적용 결과**:

| | |
|---|---|
| 제외 | SNDKB, SPCXB, SNXXB, SKHYB, KORUB, SOXLB, MUB |
| 신규 포함 | **AAVE, UNI, XLM, LTC, TAO**, RED, USDE, HEMI |
| 최소 상장 경과 | 0.1년 → **0.8년** |

### 비용

상장일은 바뀌지 않는 값이므로 BR28의 `collection_state` 캐시를 재사용한다(timeframe `1d` 키). 캐시가 있으면 조회 0회, 없으면 종목당 1회. 실측 **1초**.

훑는 범위는 거래량 상위 60종으로 제한한다 -- 전체 USDT 페어(약 500종)를 매번 확인하면 요청이 폭증한다.

**조회 실패 시에는 후보로 남긴다** -- 조회 실패로 검증된 종목이 빠지는 쪽이 신규 상장 하나를 들이는 것보다 나쁘다.

## BR41 (2026-08-20): 깊이 판정이 신선도 판정보다 먼저다

**결함**: `_collect_and_store_binance`가 `_is_up_to_date`(꼬리가 최신인가)를 **가장 먼저** 검사하고 참이면 `continue`했다. 깊이 판정(`first_time > target_start`, `_is_exchange_earliest`)은 그 뒤에 있어 **도달하지 못했다.**

그래서 **꼬리는 최신인데 머리가 얕은** 상태가 되면 영원히 그대로 남는다. 이 상태는 특별한 사고가 아니라 정상 경로로 생긴다:

1. lookback 2년일 때 정상 수집 → 2년 깊이, 꼬리 최신
2. lookback을 9년으로 확대 (2026-08-18)
3. 다음 실행부터 `_is_up_to_date` → True → **건너뜀.** 나머지 7년은 영원히 안 받는다

BR26에서 실측했듯 이력 깊이는 확률을 통째로 바꾼다 — XRP 단타 도달률이 9년 30.6% vs 1년 15.8%다. 얕은 이력으로 계산된 확률이 그대로 추천에 실린다.

이것은 문서화된 재발 계열의 5번째다: **"최초봉이 있으니 완료"** 계열의 변형인 **"최신봉이 있으니 완료"**.

**규칙**: 수집 건너뛰기는 **신선도와 깊이가 모두 충족될 때만** 허용한다.

```
backfill = _needs_backfill(...)            # 머리가 얕은가
if not backfill and _is_up_to_date(...):   # 깊이가 찼고 새 봉도 없을 때만 건너뛴다
    continue
```

`_needs_backfill`은 보유 최초봉이 `target_start` 이전이거나 거래소 최초봉과 같으면 False다. 거래소 최초봉은 BR28 캐시(`collection_state`)에서 읽으므로 **정상 상태 요청 비용은 0**이다.

**부수 수정**: `get_klines_since`가 `_MAX_PAGES`(600) 상한에 걸려 끊길 때 조용히 반환하고 있었다. `for...else`로 경고 로그를 남긴다 — 다음 실행이 이어받아 메우지만, 그동안 얕은 이력으로 확률을 계산하므로 드러나야 한다.

**검증**

- 재현 테스트: 머리 얕음 + 꼬리 최신 → 수정 전 요청 0회(건너뜀), 수정 후 `target_start`부터 백필
- BR29 회귀 테스트: 깊이까지 찬 종목은 여전히 요청 0회로 건너뜀
- 실환경 복구: XRPUSDT 4시간봉을 최근 1년(2,189봉)만 남긴 DB에 수집 1회 → **18,169봉 / 2018-05-04까지 완전 복구**
- 비용 회귀 없음: 상위 30종 x 7봉 수집 1회가 **0요청 / 0.6초** (전부 캐시 적중 + 신선)
- 전수 점검: 현재 상위 30종 x 7봉 210조합 중 얕은 조합 **0건**
